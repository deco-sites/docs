A **block** is a JSON document the CMS uses to describe one piece of content — a page, a section instance, an app configuration, or a matcher. Blocks are the unit of content versioning, A/B testing, and admin editing.

## Anatomy

Every block has a `__resolveType` field that tells the framework which code to invoke. Everything else in the JSON is the props for that code.

```json
{
  "__resolveType": "site/sections/Hero/HeroBanner.tsx",
  "title": "Welcome to our store",
  "cta": {
    "label": "Shop now",
    "href": "/products"
  }
}
```

When the framework sees `__resolveType: "site/sections/Hero/HeroBanner.tsx"`, it:

1. Looks up the section in the registry.
2. Validates the rest of the JSON against the section's `Props` interface.
3. Renders the section with those props.

## Block types

| Block type | `__resolveType` example | What it represents |
|---|---|---|
| Page | `$live/pages/Page.ts` | A page with its sections in order |
| Section instance | `site/sections/Hero/HeroBanner.tsx` | One placement of a section |
| App configuration | `deco-vtex` | VTEX or Shopify or Resend setup |
| Matcher | `site/matchers/MatchUserAgent.ts` | A flag/AB rule |
| Loader instance | `vtex/loaders/intelligentSearch/productList.ts` | A configured loader call |

## Where blocks live

### Source: `.deco/blocks/*.json`

One JSON file per block, committed to the repo. The admin syncs this directory both ways — edits in admin become files in `.deco/blocks/` and vice versa.

### Bundle: `src/server/cms/blocks.gen.json`

A single JSON object that maps block IDs to their JSON. Generated by the `generate-blocks` script:

```bash
npm run generate:blocks
```

This is what the framework actually loads at runtime. In production storefronts, `blocks.gen.json` typically ranges from a few MB to over 10 MB depending on the number of pages and sections in the CMS.

### Re-export: `src/server/cms/blocks.gen.ts`

A thin module that the [Vite plugin](/v2/en/framework/vite-plugin) replaces with `JSON.parse` of the sibling `.json` at load time. Don't hand-edit either file.

<Callout type="warning">
**Don't manually chunk `@decocms/blocks` or `@decocms/apps-*`** in `vite.config.ts`. The Vite plugin handles the JSON fast-path, and these packages have circular re-exports that crash if you split them across chunks.
</Callout>

## How resolution works

When a request comes in for `/products/some-product`:

1. The catch-all route runs `loadCmsPage({ siteName, pathname })`.
2. `loadCmsPage` calls `resolveDecoPage` from `@decocms/blocks/cms`, which:
   - Looks up the page block by URL pattern.
   - Walks each section reference in the page's section list.
   - Resolves each section's `__resolveType` to a registered component.
   - Runs each section's loader (if any).
   - Returns a tree the renderer can walk.
3. `DecoPageRenderer` walks the tree and renders each section.

See [Pages and routes](/v2/en/concepts/pages-and-routes) for how pages are matched.

## Composability

Blocks reference other blocks. A page contains section references; a section can contain a loader reference; a matcher can contain other matchers. The CMS resolves the whole graph lazily.

```json
{
  "__resolveType": "$live/pages/Page.ts",
  "path": "/products/:slug",
  "sections": [
    {
      "__resolveType": "site/sections/Header/Header.tsx"
    },
    {
      "__resolveType": "site/sections/Product/ProductDetail.tsx",
      "loader": {
        "__resolveType": "vtex/loaders/intelligentSearch/productDetailsPage.ts",
        "slug": "{slug}"
      }
    }
  ]
}
```

URL parameters (`{slug}`) are interpolated at resolution time.

## Multivariate blocks

A block can reference a matcher to A/B test or segment content:

```json
{
  "__resolveType": "$live/matchers/MultivariateBlock.ts",
  "variants": [
    { "matcher": { "__resolveType": "..." }, "block": { "__resolveType": "..." } },
    { "block": { "__resolveType": "..." } }
  ]
}
```

The first variant whose matcher returns true wins. See [Matchers and flags](/v2/en/concepts/matchers-and-flags).

## ETag and cache invalidation

The framework computes a content hash (DJB2) over the resolved blocks and exposes it as an ETag header. When you edit a block in admin and republish, the ETag changes and CDN/browser caches invalidate appropriately.

This is **not** a string-length hash — it's a real content hash, so two same-length but different-content versions invalidate correctly.
