## CSV-driven legacy redirects

```33:67:/Users/fernandofrizzatti/development/workspace/decocms/baggagio-tanstack/src/worker-entry.ts

// references `website/loaders/redirectsFromCsv.ts` with `from: "redirect.csv"`

```

**Why**: when you migrate from a legacy stack with thousands of URLs that need to redirect, putting them all in `.deco/blocks/` is impractical. A CSV file committed to the repo is easier for the team to edit and review.

**The pattern**:

1. `redirect.csv` at repo root, semicolon-separated (`from;to;status`).
2. `import redirectsCsv from "../redirect.csv?raw"` — Vite inlines the CSV as a string at build.
3. `parseSemicolonRedirectsCsv` parses once at module load.
4. `addRedirects(...)` registers them with the framework's redirect matcher.
5. The proxy handler matches inbound paths and returns 301/307 with the right `Location`.

This is the canonical migration-to-canonical-URLs pattern.

## Decofile-pruned loaders

```3:19:/Users/fernandofrizzatti/development/workspace/decocms/baggagio-tanstack/src/setup/commerce-loaders.ts
 *   3. The auto-generated `siteLoaders` map (`server/cms/loaders.gen.ts`)
 *      which the build step prunes to only the `site/loaders/*` and
 *      `site/actions/*` keys actually referenced by the CMS decofile —
 *      avoiding the "200 dead passthroughs" pattern that bloated this
 *      file before the architectural cleanup.
```

The `generate:loaders` script accepts `--decofile-dir .deco/blocks` to filter only loaders the decofile actually references:

```jsonc
"generate:loaders": "tsx node_modules/@decocms/start/scripts/generate-loaders.ts --exclude vtex/loaders,vtex/actions --decofile-dir .deco/blocks"
```

**Result**: `loaders.gen.ts` only contains the loaders that some block references via `__resolveType`. Dead passthroughs are pruned.

**Why this matters**: every loader in `loaders.gen.ts` becomes a server function in the bundle. Hundreds of unused loaders bloat the build, slow cold starts, and clutter the typed invoke client.

**Casa&Video and Le biscuit don't yet do this** — Bagaggio is the proof of concept. Strongly recommend adopting for new sites.

## `withSiteGlobals` for route-wide injection

```9:18:/Users/fernandofrizzatti/development/workspace/decocms/baggagio-tanstack/src/routes/$.tsx
const routeConfig = withSiteGlobals(
  cmsRouteConfig({
    siteName: "Bagaggio",
    defaultTitle: "Baggagio-tanstack",
    ignoreSearchParams: ["skuId"],
  }),
);
```

`withSiteGlobals` wraps the route config so site-wide data (analytics IDs, theme tokens, GTM container) is available in every route loader without copy-paste.

**The pattern**: when you have a thing every page needs, define it once in a globals helper, wrap your route configs, done.

## Custom root layout (no `DecoRootLayout`)

Bagaggio uses a bespoke `__root.tsx` instead of `DecoRootLayout`:

```tsx
// approximation
function RootLayout() {
  return (
    <html lang="pt-BR">
      <head>
        <link rel="stylesheet" href="..." />
        <link href="https://fonts.googleapis.com/..." rel="stylesheet" />
      </head>
      <body>
        <StableOutlet />
        <MinicartDrawer />
      </body>
    </html>
  );
}
```

**Why**: Bagaggio renders the minicart drawer outside the route tree (at `<body>` level so it overlays everything). `DecoRootLayout` doesn't have a slot for that.

**The takeaway**: if `DecoRootLayout` doesn't have the slot you need, roll your own — but understand you're now responsible for fonts, providers, and live-controls integration.

## Sitemap routed to `static` profile

```11:14:/Users/fernandofrizzatti/development/workspace/decocms/baggagio-tanstack/src/cache-config.ts
registerCachePattern({
  test: (p) => p === "/sitemap.xml",
  profile: "static",
});
```

Sitemap.xml gets the long-TTL `static` profile because:

- It's expensive to generate (walks the entire catalog).
- It rarely changes between catalog publishes.
- A 24-hour cache is fine; search engines re-fetch on their own schedule.

Otherwise Bagaggio uses default cache profiles.

## No A/B harness

`SITES_KV` is bound but commented out:

```jsonc
// "kv_namespaces": [
//   { "binding": "SITES_KV", "id": "..." }
// ]
```

The team's not running site-version A/B tests yet. The KV bind is ready when they need it; no `withABTesting` wrap until then.

**The takeaway**: don't add infrastructure you're not using. Worker-level A/B is opt-in for a reason.

## VTEX without region-aware fetch

```ts
setVtexFetch(createInstrumentedFetch("vtex"));
```

Plain instrumented fetch. Bagaggio's catalog has less regional variation than Casa's, so the region-aware wrapper isn't needed.

If you start seeing region-related bugs (PDP showing wrong stock, prices off), reach for the wrapped pattern.

## What to take from Bagaggio

- **Decofile-pruned loaders** (`--decofile-dir .deco/blocks`) — adopt this for new sites.
- **CSV-driven redirects** if you're migrating thousands of legacy URLs.
- **`withSiteGlobals`** when you have route-wide data injections.
- **Don't add infrastructure you're not using** — opt into A/B / regional fetch / Sentry only when needed.

## What NOT to copy verbatim

- The custom root layout — only do this if `DecoRootLayout` doesn't have the slot you need.
- The semicolon-CSV format — pick whatever delimiter your team prefers; the parser is small.
- The specific exclude list in `generate:loaders` — that's Bagaggio-specific.
