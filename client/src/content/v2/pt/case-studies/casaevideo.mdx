[Casa&Vídeo](https://www.casaevideo.com.br) é varejo brasileiro de eletrônicos e utilidades domésticas. Migraram de Fresh para v2 em 2025, e a codebase deles é a referência mais elaborada a v2 para uma loja em escala. Esta página percorre as decisões deles.

## Forma da loja

- **70+ sections** (PDPs, PLPs, prateleiras, banners, drawer, footer, vários layouts de header).
- **VTEX** com 500k+ SKUs, ~50k pedidos/mês.
- **Multi-região** (BR continental, frete e estoque variando por CEP).
- **A/B testing** maduro (canary releases).
- **Sentry, GTM, PostHog, Hotjar** integrados.
- **Internal `docs/`** com gap analysis e investigações.

[Repo](https://github.com/decocms/casaevideo-storefront).

## Padrões a copiar

### 1. Async section rendering tunado

Eles configuram fold threshold + respect CMS lazy:

```ts
// src/setup.ts
import { setAsyncRenderingConfig } from "@decocms/start/cms";

setAsyncRenderingConfig({
  foldThreshold: 3,
  respectCmsLazy: true,
});
```

Eles trataram de validações exaustivas de modo dev:

> "I/O across requests" pode aparecer em modo dev quando uma section deferred carrega após a resposta principal.

A correção deles: documentar em [`ssr-optimization-framework.md`](/Users/fernandofrizzatti/development/workspace/decocms/casaevideo-storefront/docs/ssr-optimization-framework.md) e adicionar `no_handle_cross_request_promise_resolution` em `wrangler.jsonc`.

Resultado: sections deferred carregam em scroll sem re-render parents. PDP first-paint cortou ~40%.

### 2. Fetch regional VTEX

Loja precisa de pricing por região (estado / CEP). O setup deles troca config VTEX por country header:

```ts
// src/setup/setup-vtex-fetch.ts
import { configure } from "@decocms/apps/vtex/client";
import { createInstrumentedFetch } from "@decocms/start/sdk/instrumentedFetch";

const region = request.headers.get("cf-ipcountry");
const account = region === "BR" ? "casaevideo" : "casaevideo";  // single account
const channel = mapRegionToChannel(region);

configure({ account, salesChannel: channel });
setVtexFetch(createInstrumentedFetch("vtex"));
```

Por baixo, mais lookup por CEP via [`vtex/loaders/postalCode/regionId.ts`](/v2/pt/commerce/vtex-loaders-and-actions#vtex-loaders-postalcode-regionid-ts) para refinar regionId quando o usuário entra com CEP.

### 3. Cache profile overrides

Eles overrideiam profiles em [`src/cache-config.ts`](/Users/fernandofrizzatti/development/workspace/decocms/casaevideo-storefront/src/cache-config.ts):

```ts
import { setCacheProfile, registerCachePattern } from "@decocms/start/sdk/cacheHeaders";

setCacheProfile("pdp", { maxAge: 30, sMaxAge: 600, staleWhileRevalidate: 86400 });
setCacheProfile("plp", { maxAge: 60, sMaxAge: 300, staleWhileRevalidate: 86400 });
setCacheProfile("home", { maxAge: 60, sMaxAge: 600, staleWhileRevalidate: 86400 });

registerCachePattern("/c/promocao", "home");
registerCachePattern(/^\/black-friday\/.*/, "home");
```

A intuição: PDPs e PLPs lidam com pricing/estoque que mudam, mas usuários toleram dados de até 5 min stale. Stale-while-revalidate de 1 dia cobre falhas upstream.

### 4. A/B testing via KV

Eles fazem canary deploys via `withABTesting`:

```ts
// src/worker-entry.ts
import { withABTesting } from "@decocms/start/sdk/abTesting";

export default withABTesting(decoWorker, {
  kvBinding: "SITES_KV",
  preHandler: (request, url) => {
    if (url.pathname.startsWith("/admin")) return null;
    return null;
  },
});
```

Variants no KV: `current` (90%), `canary` (10%). Cookie `_deco_variant` faz sticky.

### 5. CMS-driven redirects

Eles usam `loadRedirects` para até ~500 active redirects. Para legacy bulk usam CSV (~10.000 entradas):

```ts
import { loadRedirects, matchRedirect } from "@decocms/start/sdk/redirects";
import { matchCsvRedirect } from "./middleware/csv-redirects";

const cmsRedirects = loadRedirects(loadBlocks());

const proxyHandler = (request: Request, url: URL) => {
  const cms = matchRedirect(url.pathname, cmsRedirects);
  if (cms) return redirectResponse(cms);

  const csv = matchCsvRedirect(url.pathname);
  if (csv) return redirectResponse(csv);

  return null;
};
```

CMS para mantenance ativo, CSV para legacy bulk.

## Padrões a NÃO copiar

### Componentes específicos do site

A pasta `src/sections/` da Casa&Vídeo é fortemente acoplada a marca (brand colors, animations, copy). Não copie.

### Cache profiles inline

Casa&Vídeo override profiles para tunar perto da realidade de tráfego deles. Profiles deles são PDP=30/600 mas seu pode ser melhor servido com 60/300 default. Mensure primeiro.

### Lógica regional

Casa&Vídeo precisa de regional fetch porque BR é grande. Lojas single-region (Le biscuit) não precisam. Não adicione complexidade sem motivo.

### Sentry config

Casa&Vídeo tem reporter custom para Sentry tunado para volumes deles. Para começar, use `@sentry/cloudflare` defaults — afina depois.

## Tradeoffs

**Pros do approach Casa&Vídeo:**
- Performance é first-class (cache + async + regional tunning).
- Robust contra falhas upstream (SWR amortece).
- Engenharia rastreável via internal docs.

**Contras:**
- Mais código para manter.
- Setup steeper para novos engenheiros.
- Custom logic precisa ser reportada para framework como features universais.

Para uma loja com escala da Casa&Vídeo, vale. Para mais cedo, é over-engineering. Migre features quando o problema aparecer, não cedo.
